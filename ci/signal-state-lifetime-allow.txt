# Owners disarmed explicitly rather than by declaration order: the destructor
# BODY runs before any member is destroyed, so a disarm there closes the window
# that member declaration order would otherwise open. One entry per covered
# handler, "<path>:<owner>:<signal>:<destructor>:<disarm>". An entry that stops
# matching an inversion -- or an owner that stops being unreadable from its own
# .cpp -- fails the gate; it may not rot.
#
# The key is the owner and the SIGNAL, not a line: the disarm being amnestied
# belongs to the owner's destructor, and a line number made every entry here
# depend on the edits above it, while the owner's name alone let any local
# spelled the same way inherit the amnesty. One entry covers one handler, and
# the number of entries has to match the number of inversions found.
#
# The last two fields are read from the code, not taken on trust, and they are
# read from both ends. The gate brace-matches the named destructor and requires
# the named disarm to be in its body with comments stripped -- delete the disarm
# and the amnesty fails with it. The destructor it reads is the owner's OWN: for
# an owner declared directly in a type body, the one defined inside that body;
# otherwise the file must define that destructor exactly once -- two out-of-line
# definitions of the same short name in one file are two types, and reading
# either one for the other is the borrowing this half of the key closes. It
# also requires the amnestied owner to BE a member of that destructor's type,
# and it asks that of the two shapes below in the terms each one allows: an
# owner declared in the .cpp must be declared DIRECTLY in the type's body, so a
# local in a free function -- or in one of the type's own member functions --
# inherits nothing; an owner declared in a header has no declaration here to
# read, so what is required of it is that the registration happens from inside
# the type. That second reading is the weaker of the two, and it is as strong
# as the .cpp gets.
#
# What this does NOT establish is that "the type" is one type: both readings
# above key on a class/struct tag read by its LAST identifier segment, with no
# namespace and no notion of two distinct types sharing a segment. An owner
# declared directly inside a second, differently-scoped type of the same short
# name as the one an entry names -- its own destructor, however it reads --
# still matches "member of <name>" and "destructor named ~<name>" the same way
# the real owner does. Known door, not closed by this key.
#
# To add an entry: run the gate, take the file and line it reports, read the
# owner's destructor, and write the destructor and the disarm statement you find
# there -- whitespace is insignificant on both sides, so copy it as it reads. An
# entry is never derived from the gate's output alone; the last two fields are a
# claim about the code that somebody has to have checked. To refresh one after a
# rename, change the field that renamed; nothing here depends on line numbers.
#
# Two shapes land here. An owner declared in the .cpp with state below it, and
# an owner declared in a HEADER, whose order against the state its handler
# touches cannot be read from the .cpp at all. The second is reported by the
# gate rather than skipped, so it cannot be amnestied by accident.
